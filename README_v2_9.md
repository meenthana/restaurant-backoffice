## วิธีเปิดใช้กับฐานข้อมูลเดิม
1. เปิด MySQL ใน XAMPP และเข้า phpMyAdmin ตามที่เครื่องร้านใช้อยู่
2. Export ฐานข้อมูล restaurant_backoffice ทั้ง structure และ data เก็บไว้ก่อน ชุด source backup ไม่ทดแทน SQL backup
3. เลือกฐานข้อมูล restaurant_backoffice แล้ว Import เฉพาะ sql/migration_v2_9_service_flow.sql หรือไฟล์ชื่อเดียวกันที่แนบรายงานนี้
4. ไฟล์นี้เพิ่ม 3 ตาราง เปลี่ยน LINE ID ให้เป็น NULL ได้ และเพิ่ม adjustment ใน enum สต๊อก ไม่มีคำสั่งลบออเดอร์หรือ reset แต้ม แต่ ALTER TABLE มี implicit commit
5. อย่าใช้ install_v2_full.sql กับฐานข้อมูลเดิม ไฟล์นั้นไว้ติดตั้งฐานข้อมูลใหม่เท่านั้น
6. เปิดหลังร้าน → จัดการ → รายงานบริการ / ตั้งค่าประเภทเมนู ตั้งเครื่องดื่มหรือเมนูที่ไม่นับเป็นจาน
7. โหลดหน้าตู้ใหม่ หากยังเห็นข้อความรอ migration ให้ตรวจว่าติดตั้ง SQL ถูกฐานข้อมูล
8. ทดสอบออเดอร์ใหม่ครบวงจรด้วยข้อมูลทดสอบก่อนใช้รับเงินจริง

ถ้า schema จริงไม่ตรงกับ SQL dump ที่ส่งมา ให้หยุดตรวจ error ก่อน ไม่ import ไฟล์ติดตั้งใหม่ทับเพื่อแก้ปัญหา

## วิธีใช้งานใหม่
- ตู้: เลือกทานที่ร้าน/กลับบ้าน → สมาชิกหรือบุคคลทั่วไป → เมนู → การรับใบเสร็จ → วิธีจ่าย
- หน้าเสร็จแสดงเลขคิว QR ติดตาม และรหัสรับอาหาร 6 หลัก ให้ลูกค้าบันทึกก่อนหน้าจอกลับหน้าแรก (60 วินาที)
- QR ติดตามไม่ใช่ QR พร้อมเพย์และไม่ใช่ QR ส่งสลิป; คนมีลิงก์อ่านออเดอร์ได้ จึงไม่ควรส่งต่อ
- เงินสด: รับเลขคิวแล้วจ่ายแคชเชียร์; จ่ายครบแล้วครัวจึงเห็นใบงาน
- ครัว: เริ่มทำ → พร้อมรับ; งานใหม่ที่ใช้รหัสรับอาหารต้องให้แคชเชียร์ส่งมอบ
- เสียงครัว: เปิดไมค์ → เช่น “เริ่มทำ เอ 23” → ตรวจข้อความบนจอ → “ยืนยัน” หรือ “ยกเลิก”; หากระบบหยุดฟังให้กดเปิดใหม่
- แคชเชียร์: กรอกรหัส 6 หลักจากลูกค้าแล้วกดส่งมอบ; ผู้จัดการ/เจ้าของตรวจหลักฐานแทนได้โดยใส่เหตุผล 10–255 ตัวอักษรและมี log
- เลขคิวอย่างเดียวไม่ใช่หลักฐานรับอาหาร; ลูกค้าไม่บันทึกรหัสให้ผู้จัดการตรวจหลักฐานชำระ
- ออเดอร์ Kiosk v2.9 ที่ออกเลขแล้วจะไม่แก้รายการเดิม: หากยังไม่จ่ายให้ยกเลิกแล้วสั่งใหม่ เพื่อไม่ให้ประเภท/เลขคิวเปลี่ยนหลังลูกค้าบันทึก
- บิลเก่าที่ไม่มี snapshot จะไม่ถูกอ้างว่าเก็บ VAT ณ เวลาขายไว้แล้ว

## ผลตรวจสอบที่ทำจริง
- ตรวจ syntax PHP 113 ไฟล์
- ตรวจ syntax JavaScript 6 ไฟล์
- ทดสอบผ่าน 3,617 assertions (ส่วนใหญ่เป็นการกระทบยอด VAT หลายจำนวนเงิน) ของตรรกะและวงจรออเดอร์ด้วย SQLite ในหน่วยความจำและตัวแปลงไวยากรณ์ SQL สำหรับทดสอบเท่านั้น ครอบคลุม VAT ระดับสตางค์ การ normalize เบอร์ การสมัคร/ใช้สมาชิกเดิม การจ่ายและส่งครัว token ผิด รหัสรับผิด รับซ้ำ แต้ม การแก้เบอร์ ข้อมูลเบอร์ซ้ำ และ rollback เมื่อเขียน log ไม่ได้
- ตรวจ DOM ที่ render จากหน้า Kiosk: 73 ID ไม่ซ้ำ และ element ที่ JavaScript อ้างถึงมีอยู่
- ตรวจว่า guest ยังสั่งได้เมื่อไม่มีตาราง v2.9 และระบบปฏิเสธการใช้สมาชิกใหม่จนกว่าจะติดตั้ง migration
- ทดสอบ parser เสียงผ่าน 18 assertions ด้วยข้อความทั้งตัวเลขอารบิก เลขไทย และคำจำนวนไทย รวมคำสั่งที่ต้องปฏิเสธ

SQLite ไม่ทดแทนการทดสอบ MariaDB: ยังไม่ยืนยัน DDL, row locking, concurrency หรือพฤติกรรมเครือข่ายจริง และยังไม่ได้ตรวจหน้าตาบนเบราว์เซอร์/ตู้จริง เครื่องพิมพ์ หรือเสียงจากไมโครโฟน

## ชุดตรวจรับก่อนใช้งานร้าน
1. บุคคลทั่วไปไม่ถูกผูกสมาชิกของคนก่อน; เริ่มใหม่/หมดเวลาล้างชื่อ เบอร์ รหัส และลิงก์จากหน้าตู้
2. สมัครเบอร์เดียวกันจากสองตู้ ไม่เกิดสมาชิกซ้ำ; เบอร์ซ้ำในข้อมูลเก่าให้ตรวจแทนการรวมเอง
3. จ่ายครั้งเดียวส่งครัวครั้งเดียว; การ retry คำขอเดิมใน session คืนออเดอร์เดิม
4. ก่อนจ่ายเข้าครัวไม่ได้; หลังจ่ายเปลี่ยนรายการผ่านเส้นทางแก้เดิมไม่ได้
5. ศูนย์สต๊อกยังขายได้ แต่ปิดขายด้วยมือยังป้องกันการสั่ง
6. 1 จานเป็น A, หลายจานเป็น B, รายการไม่นับจานอย่างเดียวเป็น C
7. Token ผิด/หมดอายุไม่เห็นออเดอร์; รหัสรับผิด/รับซ้ำไม่ปิดงาน; ผู้จัดการแทนรหัสต้องมีเหตุผล
8. ไม่รับกระดาษไม่สั่งพิมพ์เอง; ขอพิมพ์มี log แต่ไม่ถือว่าเครื่องพิมพ์สำเร็จ
9. ยอด VAT + ฐานภาษีตรงยอดรวม และไม่เปลี่ยนย้อนหลัง; รายงานเงินคืนต้องไม่ปะปนกับยอดขายเดิม
10. เสียงกำกวมไม่เปลี่ยนสถานะ; คำว่า “ยืนยัน” ลอย ๆ หรือหมดเวลาต้องไม่ทำงาน

## ร่างเนื้อหารายงานโครงงาน
ปัญหา: การสั่งหน้าร้านต้องพึ่งพนักงาน ลูกค้าไม่ทราบสถานะอาหาร อุปกรณ์คิวมีจำนวนจำกัด และการพิมพ์ใบเสร็จทุกครั้งใช้ทรัพยากร
วัตถุประสงค์: ให้ลูกค้าสั่งเอง ระบุสมาชิกด้วยเบอร์หรือไม่สมัคร ติดตามอาหาร และเลือกการรับกระดาษ; แยกงานครัวกับแคชเชียร์และตรวจย้อนหลังได้
ขอบเขต: เว็บ PHP/PDO บน XAMPP/MariaDB; Kiosk, Cashier, Kitchen, จอติดตามและหลังร้าน; Soft Stock ไม่ใช่ระบบคงคลังอัตโนมัติ
หลักการออกแบบ: state machine, server-side validation, transaction, token แบบเก็บ hash, role/CSRF, idempotent retry ใน session และบันทึกภาษี ณ เวลาจ่าย
วิธีประเมินที่ต้องทำต่อ: วัดเวลาสั่ง เวลารอ ความถูกต้องของการส่งมอบ สัดส่วนไม่พิมพ์ และอัตราคำสั่งเสียงถูกต้องในสภาพเงียบ/เสียงรบกวน โดยระบุจำนวนผู้ทดลอง อุปกรณ์ และเกณฑ์สำเร็จก่อนเก็บข้อมูล
ผลการทดลองจริง: ยังไม่ได้เก็บ ห้ามใช้ผล automated test เป็นตัวเลขความพึงพอใจหรือความแม่นยำเสียงของผู้ใช้จริง
